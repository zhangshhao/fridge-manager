# 部署、备份恢复与维护

## 状态与资源

本机开发不需要云资源。正式环境需要 Docker Compose、有效域名及 HTTPS、模型服务账号、独立数据库、异机备份目标和实际联系渠道。大陆部署按实际主体和服务范围处理域名备案与 AI 服务相关要求。

本仓库没有真实生产密钥。`.env`、`.env.production`、`.local`、数据库导出及备份都被 Git 忽略。生产文件仅放在服务器受限目录，权限 `600`。不要把导出放在静态网站目录。

开发版本：Node 24.14、React 18.3.1（与 Ant Design Mobile 5.41.1 兼容）、TypeScript 5.9.3、Vite 7.3.7、Fastify 5.12.7、Prisma 6.19、PostgreSQL 18。具体版本及传递依赖以 package-lock.json 为准。`effect`、`deepmerge-ts` 使用已修复依赖覆盖，已对生成、迁移和运行做验证。

## 首次部署

以下命令在服务器仓库根目录执行。建议 `/opt/fridge-manager`，2 核 4GB 起步。防火墙只开放实际需要的 SSH、80、443。数据库和 API 不映射宿主机端口。

1. 从 `deploy/production.env.example` 复制为 `.env.production`，填写域名、邮箱、数据库长随机密码与 URL、百炼账号实际模型、AI 密钥、隐私联系渠道、远程 Restic 仓库及加密口令。URL 中密码需正确转义。
2. 域名 A/AAAA 解析到服务器。Caddy 自动申请 HTTPS。确保 APP_ORIGIN 与浏览器地址精确一致。
3. 构建并启动：

```sh
docker compose --env-file .env.production -f deploy/compose.yaml build
docker compose --env-file .env.production -f deploy/compose.yaml up -d
docker compose --env-file .env.production -f deploy/compose.yaml ps
```

`migrate` 等待数据库健康后执行迁移，成功后 API 才启动，API 健康后 Caddy 才启动。固定 RELEASE 对应镜像标签，不使用 latest。

4. 在受控终端设置初始化账号环境变量，再传入一次性容器。避免把真实密码直接写进共享命令记录：

```sh
export ADMIN_USERNAME FAMILY_NAME ADMIN_PASSWORD
docker compose --env-file .env.production -f deploy/compose.yaml run --rm -e ADMIN_USERNAME -e ADMIN_PASSWORD -e FAMILY_NAME api npx tsx scripts/admin.ts
unset ADMIN_PASSWORD
```

初始化脚本拒绝覆盖已有账号。不要运行生产演示种子。

5. 检查 `https://域名/api/health`、登录、邀请、入库、AI、确认整餐及撤销。用目标手机完成安装、重新打开、软键盘、安全区和弱网验证。实测单次模型用量、耗时及费用，再调整模型和限额。模型供应商预算限额需另在平台设置。

## 已有 Nginx 的子路径部署

`https://zzhao.cc.cd/fridge-manager/` 使用服务器已有的 Nginx 和 HTTPS 证书，应用目录为 `/opt/fridge-manager`。数据库和 API 使用 Docker Compose，API 仅绑定宿主机 `127.0.0.1:3001`。保留已有站点和 `/SBTI/` 路由，不启动 Compose 中占用 80/443 的 `web` 服务。

生产环境配置：

```dotenv
APP_ORIGIN=https://zzhao.cc.cd
APP_BASE_PATH=/fridge-manager
RELEASE=1.0.1
```

`APP_ORIGIN` 仅包含协议与主机，不能带路径，因为浏览器 Origin 请求头不包含路径。前端构建时的 `VITE_BASE_PATH=/fridge-manager/` 由 `deploy/compose.nginx.yaml` 传入；资源地址、API、PWA 安装范围和邀请链接都使用此路径。

首次部署或升级，在应用目录执行（升级前先备份数据库）：

```sh
docker compose --progress plain --env-file .env.production -f deploy/compose.yaml -f deploy/compose.nginx.yaml build api
docker compose --progress plain --env-file .env.production -f deploy/compose.yaml -f deploy/compose.nginx.yaml up -d api

# 从刚构建的镜像取出同一版本的静态资源。
release=$(sed -n 's/^RELEASE=//p' .env.production)
container=$(docker create "fridge-api:$release")
mkdir -p /opt/fridge-manager/fridge-manager
docker cp "$container:/app/apps/web/dist/." /opt/fridge-manager/fridge-manager/
docker rm "$container"
find /opt/fridge-manager/fridge-manager -type d -exec chmod 755 {} +
find /opt/fridge-manager/fridge-manager -type f -exec chmod 644 {} +
```

复制 `deploy/nginx-fridge-manager.conf` 到 `/etc/nginx/snippets/fridge-manager.conf`，在现有 HTTPS `server` 块内加入 `include /etc/nginx/snippets/fridge-manager.conf;`。先备份现有配置，再执行 `nginx -t && systemctl reload nginx`。代理保留同源保护，将会话 Cookie 限制到应用路径，并关闭应用访问日志以避免记录邀请令牌。

维护与验证：

```sh
docker compose --env-file .env.production -f deploy/compose.yaml -f deploy/compose.nginx.yaml ps
docker compose --env-file .env.production -f deploy/compose.yaml -f deploy/compose.nginx.yaml logs --tail=100 api
curl -fsS https://zzhao.cc.cd/fridge-manager/api/health
```

首次部署创建独立的正式管理员和空家庭，不运行演示数据。管理员初始凭据仅保存在服务器 `/root/fridge-manager-admin.env`（权限 `600`），不提交 Git；登录后可在“我的 → 修改密码”更换。AI 参数和密钥保存在服务器 `.env.production`（权限 `600`），现有实例使用 `gpt-6.1-sol`，已验证兼容 Chat Completions 请求。异机备份目标尚未配置；本地菜谱无需密钥即可使用。

更新 AI 配置时，修改服务器 `.env.production` 中的 `AI_BASE_URL`、`AI_API_KEY`、`AI_MODEL` 及超时/限额参数，再执行下面的命令以载入新环境变量；仅执行 `restart` 不会更新容器环境。当前 `AI_TIMEOUT_MS=90000`，Nginx `proxy_read_timeout=120s`，代理等待时间应大于应用超时。

```sh
docker compose --progress plain --env-file .env.production -f deploy/compose.yaml -f deploy/compose.nginx.yaml up -d --no-deps --force-recreate api
```

## 备份

备份容器使用 `pg_dump -Fc`，经 Restic 加密上传到独立存储。密钥和备份密码分别保管，遗失 Restic 密码无法恢复。仓库不能仅放在同一云盘。数据库不暴露公网，备份容器连接内部网络。

首次初始化远程仓库：

```sh
docker compose --env-file .env.production -f deploy/compose.yaml --profile maintenance run --rm backup init
docker compose --env-file .env.production -f deploy/compose.yaml --profile maintenance run --rm backup
```

安装 `deploy/fridge-backup.service` 和 `.timer` 到 systemd，按实际目录修改 WorkingDirectory，启用 timer。每日上海时间 03:00 执行，随机延迟不超过 10 分钟。按固定主机及文件名分组保留 7 份日备份和 4 份周备份。每次备份执行仓库一致性检查；失败返回非零，成功时间保存在 `backup_state` 卷。

`BACKUP_SUCCESS_URL`、`BACKUP_FAILURE_URL` 可接入现有健康检查平台。还需在云监控或宿主机监控配置：外部 HTTPS 健康、容器异常、磁盘空间、备份超过 26 小时未成功和 AI 失败率。仓库提供日志、健康检查和回调，实际通知渠道及告警阈值需部署时配置。

每日备份意味着最坏可能丢失最近 24 小时记录。定期恢复演练比仅检查文件存在更可靠。

## 恢复到独立环境

先部署独立数据库/测试实例，不对运行中的生产库直接覆盖。暂停目标实例业务写入，使用同版本 PostgreSQL 客户端。

在具备 Restic 凭证的受限运维环境查看快照并取回：

```sh
restic snapshots --host fridge-manager --tag fridge
restic dump SNAPSHOT_ID fridge.dump > /private/restore.dump
```

创建独立目标数据库后：

```sh
pg_restore --dbname="$RESTORE_DATABASE_URL" --no-owner --no-acl --exit-on-error /private/restore.dump
```

为目标 API 配置独立数据库、会话环境和域名，执行数据核对工具，检查家庭关系、批次、流水、餐次、审计及登录。恢复旧快照会恢复其中会话，正式切换前通过维护 SQL 清除 Session，要求重新登录。确认后再决定切换流量。明文临时 dump 按运维政策销毁。

本机提供一次性演练脚本 `npm run recovery:check`，从开发数据库备份并恢复到新的 `fridge_recovery_test`。嵌入式数据库只带服务端，Windows 首次执行 `python scripts/pg-client.py`，从固定版本的 EDB 官方 HTTPS 归档取得 pg_dump/pg_restore 到 `.local/pg-client`；也可用 `PG_CLIENT_BIN` 指定已安装的同主版本客户端目录。目标库或 dump 已存在时拒绝覆盖。报告在 `.local/recovery-report.json`。演练文件仅在本机，生产备份另走 Restic 加密；不把本机演练等同于生产异机恢复验收。

## 升级与回退

1. 先运行一次备份并确认结果。记录当前镜像 RELEASE。
2. 在独立测试数据库验证迁移和测试。结构变化优先向后兼容。
3. 构建新 RELEASE，执行迁移后更新服务，检查 health 与核心流程。
4. 回退可切换旧镜像，但数据库迁移不会自动回退。不兼容结构必须走已演练的数据库恢复/修复方案。

Docker 主机没有在本机提供，因此镜像构建、Compose 编排、Caddy 发证、远程备份及 systemd 调度仍需目标主机验证。

## 数据核对、导出与删除

在维护环境设置 DATABASE_URL，先从管理员账号确认家庭 ID（`GET /api/me` 返回），再运行：

```sh
npm run data:manage -- reconcile FAMILY_ID
npm run data:manage -- export FAMILY_ID /private/family-export.json
```

核对按批次比较 Ledger 总和与 remaining。导出以事务一致快照保存家庭、成员用户名、食材、批次、餐次、审计、流水及 AI 调用，不含密码哈希、会话、邀请令牌和密钥。文件使用仅创建不覆盖模式，Unix 权限 600；Windows 请将目录 ACL 限制到当前用户。

确认主体授权、导出可读、备份可用后，显式设置 `CONFIRM_DELETE_FAMILY_ID` 等于待删除 ID，再执行 `npm run data:manage -- delete FAMILY_ID`。该操作不可撤销；删除家庭业务数据及成员关系，保留用户账号（其可能属于其他家庭），加密备份按保留周期过期。账户彻底删除需先处理其所有家庭关系，由部署管理员按隐私请求执行。维护脚本不开放公网下载入口。
